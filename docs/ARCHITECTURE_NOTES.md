# Architecture Notes — EventFlow Practice 05

## 1. Research Summary
We reviewed official documentation and reference patterns for:
1. **`mobile_scanner` (pub.dev)**: Supports Android (CameraX/ML Kit), iOS, macOS, and Web (ZXing/jsQR; requires secure context or `localhost`). Does **not** support Windows desktop. Therefore, Windows uses a unified manual-entry / USB-HID keyboard-wedge input path feeding the exact same `CheckInRepository.submitCheckIn()` server call.
2. **FastAPI + `sse-starlette` + `asyncpg`**: Using `EventSourceResponse` with an in-process asyncio pub/sub broadcaster (and optional Postgres `LISTEN/NOTIFY` bridge) after transaction `COMMIT` ensures clients never see uncommitted state and receive updates in well under 3 seconds.
3. **Flutter SSE Client with Auto-Reconnect**: A custom `http.Client` streaming parser (`utf8.decoder` + `LineSplitter`) wrapped in a `StreamController` with exponential backoff (1s, 2s, 4s, max 15s) and `Last-Event-ID` / full state resync on reconnect avoids fragile third-party SSE packages and works identically on Android, Web, and Windows.

## 2. Adopted Patterns
- **Clean 3-Layer Flutter Architecture**:
  - `UI / presentation`: Adaptive screens (`< 768 px` bottom nav + cards, `>= 768 px` / `1280 px` navigation rail + tables/split panels), `lib/design/tokens.dart` design system.
  - `Application / domain`: `ChangeNotifier` / `ValueNotifier` controllers per role + shared `AuthStore` and `SyncStore`.
  - `Data / repository`: `ApiClient` (REST), `SseClient` (auto-reconnect), `LocalCache` (read-only offline display cache with explicit offline banner; never authorizes entry).
- **Single Source of Truth on Server**:
  - All timestamps (`issued_at`, `used_at`, `cancelled_at`, `server_time`) are generated by PostgreSQL / FastAPI UTC clock.
  - Deterministic lock ordering (`events` -> `ticket_types` -> `tickets`) with `SELECT ... FOR UPDATE` prevents deadlocks and guarantees atomic last-seat and single-entry invariants.
  - `UNIQUE(ticket_id)` on `entries` and partial unique index `uq_active_ticket_per_user_event` on `tickets` enforce invariants at the database layer even if application code has a bug.

## 3. Rejected Patterns & Why
- **Client-side "read then write" check-in**: Rejected because two concurrent scanners would both read `ISSUED` and allow double entry.
- **Polling every N seconds instead of SSE**: Rejected by spec (§13); polling is only a fallback/resync on reconnect, never the primary sync mechanism.
- **Local SQLite as primary store**: Rejected by spec (§11); local storage is strictly a read-only cache with offline indicator.
- **Storing plain QR tokens in `audit_logs` or error responses**: Rejected for security (§9); only `token_hash` (SHA-256) is indexed, and `token_encrypted` (Fernet) is decrypted only for the ticket owner.
